## Bug found and fixed during this run

**`DEFAULT_VISIT.type` rejected by API ([visit-section.tsx:18](../../src/components/report/accident-info/visit-section.tsx#L18))**

When a user clicked **Add Visit**, the new row's `type` field defaulted to `''` (empty string). The visit-saving Zod schema (`visitSchema` in [accident-info.ts:62](../../src/lib/validations/accident-info.ts#L62)) expects either `'claimant_residence'`, `'claimant_office'`, or `'other'`. Empty string failed validation → API returned 400.

Worse: `useAutoSave` retains the failing payload to retry, so the **next** PATCH for accident-info (e.g. opening Expert Opinion and typing) included the still-broken visit data and **also got rejected**. Net effect: visits never saved, and any expert-opinion edit made while a half-filled visit existed also silently failed.

Fixed by defaulting `type` to `'other'`. After fix, KG/OT verified visits + expert opinion in the PDF.

## Issue #1 — HS calculation tab values not persisting

| Expected | What the PDF shows |
|---|---|
| `Replacement Value 12.500,00 €` | *(field empty)* |
| `Residual Value 8.200,00 €` | *(field empty)* |
| `Diminution in Value 1.800,00 €` | *(field empty)* |
| `Damage Class III` | `Damage Class I` (AI value) |
| `Repair Method Instandsetzung` | `Conventional body repair with paint correction` (AI value) |
| `Risks Korrosionsgefahr` | `Paint may have penetrated…` (AI value) |
| `Body Paint Panel repaint` | `Body Paint Spot repair` (AI value) |
| `Cost per Day 35,00 €` | *(missing)* |
| `Repair Time 5 days` | `Repair Time 1 days` (AI value) |
| `Replacement Time 12 days` | *(missing)* |

Looking at the DB after the test, every one of these values is **either null or the AI-generated value**. Two separate problems mixed together:

1. **AI's damage-analyzer writes calc fields after the user lands on the page.**
   The damage-analyzer pipeline writes to the `calculation` table (`repairMethod`, `risks`, `damageClass`, `bodyPaint`, `plasticRepair`, `repairTimeDays`) — see [generate/route.ts:595-618](../../src/app/api/reports/[id]/generate/route.ts#L595-L618).
   For the Audi A6 photo set, the damage-analyzer fires; for the Opel Corsa and Aston Martin sets, the calc-extractor output is empty so this race doesn't trigger. That's why KG/OT pass and HS fails.

2. **Even the fields AI doesn't write (`replacementValue`, `residualValue`, `diminutionInValue`, `costPerDay`, `replacementTimeDays`) end up null.**
   The user (and the test) types them in, but they never make it to the DB. The page's `handleFieldBlur` route is correct ([calculation/page.tsx:137-167](../../src/app/(app)/reports/[id]/details/calculation/page.tsx#L137-L167)) and the watch-driven save fires for each field. My current hypothesis is that the `useAutoSave` batching collapses many rapid field changes into a single PATCH where the float-coerced empty values overwrite the just-typed integers — needs a focused debug session in [use-auto-save.ts](../../src/hooks/use-auto-save.ts) (compare against KG where the same helper saves the same field set successfully).

**Suggested remediation before client delivery:**
- Short-term: re-fetch + re-fill the calculation tab once after the AI Generate completes (the spec already does a wait, but on HS it isn't enough).
- Mid-term: in the generate route, **don't overwrite** calculation fields that already have a non-default user value. Or stop the damage-analyzer from writing user-editable fields entirely and surface them as *suggestions* in the UI instead.
- For the empty-numeric saves: add a Playwright integration test that fills one calc field at a time with a 1s gap and asserts each shows in the PDF — that will pinpoint whether the race is in batching or in the field-array flush.

## Issue #2 — `claimantLicensePlate` overwritten by AI OCR

The PDF shows `License Plate FÜ B 147` (AI-extracted from the photo) instead of the typed `B AB 1234`. Same root cause as Issue #1: AI's plate-OCR write happens after the user's PATCH on accident-info — see [generate/route.ts:308-316](../../src/app/api/reports/[id]/generate/route.ts#L308-L316).

The route has an explicit comment: `// license plate may be re-detected; OK to overwrite`. Whether that's actually OK depends on stakeholder intent — but in the test, **the user's manual override loses to a later AI write**, which is almost certainly not the desired UX.

Note that BE/KG/OT also went through AI generate, but their photos didn't contain a clearly readable plate, so the AI plate value matched the user input or was empty, and there was no visible conflict. Same race, just not surfaced.

## Issue #3 — BE invoice line items missing (1 instance)

The BE PDF says `No line items` even though the test filled `Bewertungsgutachten Quattroporte` at rate `450.00`. The exact same `fillInvoice` helper produced correct invoice rows on HS, KG, and OT. Reproducing the failure would require a re-run; current evidence suggests a one-shot timing flake on the "Add Row" click + first fill, **not** a structural bug (no other run has shown the line-item path failing).

**Mitigation in helper:** after `Add Row`, assert that `lineItems.0.description` is editable before fill, with a longer wait. The current 500ms gap may not always be enough on a fresh page.
