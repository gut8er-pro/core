One module answers every per-type question. Consumers read policy, never the raw string. New type = one config row + exhaustiveness check.

Problem

The report type is a bare nullable string; the same rule ("BE/OT hide accident info", "OT says Client not Claimant") is re-expressed 3–4× and the copies have already drifted.

Solution

A reportTypePolicy module keyed by a config table, exposing questions instead of a string. Every branch site calls it.

Wins
  • Leverage: one interface, 11 call sites
  • Locality: type rules concentrate in one module
  • PDF stops diverging from the form
  • New type is a config row, not a file hunt
  • Exhaustive union kills silent HS fallthrough
  • Delete 3 inline union redeclarations
Latent bug this surfaces: for BE, the correction section renders in the form but is not counted by use-tab-completion — the meter can never reach 100%.

Worth exploring in-process

Before — fetch + map + render welded

No injection, no exposed view model. The 215-line map can't be tested without a database; zero PDF tests exist. ReportPdfDocument itself is already deep — the fetch/map welding is what seals it shut.

After — three modules, one seam
loadReport(db, id, userId)
buildReportView(row): ReportView
pure · testable · assertable
render(view) → buffer
Problem

The view model can't be obtained without hitting the DB, so the biggest, most bug-prone part — the mapping — is untestable. Locale rides along too: dates and currency are hardcoded de-DE so EN PDFs still print German dates, and formatDate exists in triplicate.

Solution

Expose buildReportView as a pure module between an injected loadReport and render; fold the three date/number helpers into one locale-aware formatting module.

Wins
  • View-model mapping testable without a DB
  • Locale honored for dates + currency
  • Delete two duplicate formatDate
  • Assert on the view, not a PDF binary
Cross-cut with Card 3: pipeline.ts imports normalizeConditionValue from the PDF layer — a renderer concern leaking upstream into AI aggregation. The formatting/enum module is the natural home for it.

Problem

Solution

Extract each tab into its own module that accepts its data (and an upload port), so it renders and tests in isolation. Decide Templates: wire a backend or delete the stub.

  • Injected data seam → each tab testable
  • Supabase upload behind a port
  • The mock stub stops masquerading as a feature
Speculative because the deepening here is mostly locality + testability, not new leverage — the router-level SettingsPage orchestrator is already deep. Lower priority than 1–5.

Top recommendation

Start with Card 1 — the report-type policy module. Strong

Best leverage-to-risk of the seven. It's a pure in-process module with no runtime dependencies, so it's the safest to adopt incrementally and the easiest to test in isolation — yet it pays back across 11 call sites, ends the copy-drift where the PDF contradicts the form, and turns "add a report type" from an 11-file hunt into one config row. It also gives the other cards a vocabulary: calculationVariant(type) is exactly what the PDF (Card 6) and tab-completion should ask instead of re-deriving isBE/isOT.

Highest correctness payoff follow-up: Card 5 — child-collection persistence, where three divergent "replace-all" strategies are currently compensating for each other's duplicate-row bugs.
