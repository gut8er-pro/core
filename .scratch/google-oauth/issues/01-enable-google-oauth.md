# 01 — Enable Google sign-in

Status: ready-for-agent
Type: bug

> *This was generated by AI during triage.*

`/login` shows a "Mit Google anmelden" button that cannot succeed for any user. The app-side
code is complete and correct; the Google provider has never been configured on the Supabase
project, so there is no OAuth client for it to use.

## Verified against the live project (2026-09-13)

```
GET /auth/v1/settings             → enabled providers: ['email']   (google: false, apple: false)
GET /auth/v1/authorize?provider=google
                                  → 400 "Unsupported provider: provider is not enabled"
```

`signInWithOAuth` gets that 400, `src/lib/auth/actions.ts:223` redirects to
`/login?error=oauth_failed`, and the login page renders its generic `callbackError`. So the
failure is visible but unexplained — it does not dead-end silently.

## Code — already done, nothing to build

- `signInWithGoogle` (`src/lib/auth/actions.ts:213`) → `signInWithOAuth({ provider: 'google',
  redirectTo: appUrl('/auth/callback') })`.
- `src/app/auth/callback/route.ts` exchanges the code for a session **and** creates the
  Prisma `User` row on first OAuth signup.
- `/login` surfaces `?error=` (added on the password-reset branch).
- The implicit-flow change from ADR 0002 is scoped to `createLinkMailerClient()` alone
  (`src/lib/supabase/server.ts:55`). The default `createClient()` is still PKCE, so the
  `?code=` exchange in the callback is unaffected. Checked explicitly — this was the one
  plausible code-level conflict.

## Prerequisite — done, no longer blocking

The Supabase redirect allow-list now covers the app host. Re-probed after
`.scratch/marketing-app-split/issues/06` was closed:

```
https://app.gut8erpro.de/auth/callback                    → preserved ✓
https://app.gut8erpro.de/auth/callback?next=/reset-password → preserved ✓
https://gut8er-pro.vercel.app/auth/callback               → preserved ✓
http://localhost:3000/auth/callback                       → preserved ✓
https://definitely-not-allowed.example.com/x              → collapses to https://app.gut8erpro.de/
```

The control probe doubles as proof the Site URL is now `https://app.gut8erpro.de`. Had this
still been unset, Google sign-in would have succeeded at Google and then landed on the wrong
host with the session in a fragment, never reaching `/auth/callback`.

## Configuration — human, in two dashboards

### Part A — Google Cloud Console (`console.cloud.google.com/auth`)

1. **Audience** → *External*. Leave it in **Testing** and add your own address under *Test
   users* for now (see Part C for why it cannot stay there).
2. **Branding** → app name `Gut8erPRO`, user support email, developer contact.
   Do **not** upload a logo yet — a logo upload triggers Google's brand-verification queue.
3. **Clients → Create client → Web application.** Under *Authorized redirect URIs* add
   exactly this, and nothing else:

   ```
   https://cqgzckghgoyzijxgbncw.supabase.co/auth/v1/callback
   ```

   Google redirects to **Supabase**, never to the app. `app.gut8erpro.de/auth/callback` does
   not belong here — that URL belongs to Supabase's redirect allow-list, which is already set.
   If the console asks for an *Authorized domain*, it normally adds `supabase.co` itself.
4. Copy the **Client ID** and **Client secret**.

### Part B — Supabase (Authentication → Sign In / Providers → Google)

5. Enable the provider, paste the Client ID and Client secret, save. Leave *Authorized Client
   IDs* empty — that field is for native apps and Google One Tap, neither of which this uses.
   Paste the secret straight into the dashboard; do not route it through an agent session or a
   script, per the precedent set in `.scratch/marketing-app-split/cutover-wizard.sh`.

### Part C — before real users can sign in

Testing mode caps sign-in at the listed test users and expires refresh tokens after 7 days, so
the consent screen has to reach **Production**. That needs a reachable privacy policy, and
right now there isn't one:

```
https://gut8erpro.de/            → HTTPS unreachable (no certificate)
http://gut8erpro.de/legal/…      → 200, but it is the united-domains parking page
dig gut8erpro.de A               → 89.31.143.90  (registrar, not Vercel)
```

The Astro marketing site at `../website` is built and carries all four legal pages, but it has
never been deployed — `.scratch/marketing-app-split/issues/07` (Vercel project, env, DNS) and
`10` (cutover) are both still open. Until the apex serves
`https://gut8erpro.de/legal/datenschutz` and `/legal/impressum`, the consent screen cannot be
completed honestly — and separately, a German commercial site with no reachable Impressum is a
§5 DDG exposure that outranks this ticket.

6. Deploy the marketing site to the apex (tickets 07 + 10).
7. Verify `gut8erpro.de` in Google Search Console under the same account.
8. Consent screen → homepage, privacy policy, terms → **Publish to Production**. With only
   `openid`, `userinfo.email` and `userinfo.profile` — all non-sensitive — this needs no
   Google review.

**Order.** A and B together give a working sign-in for test users immediately and are safe in
isolation. C gates opening it to real users.

## Why this cannot be delegated

Same wall as `.scratch/password-reset-recovery/issues/01`: the Supabase MCP server exposes
migrations, SQL, logs, advisors and branches — no auth-configuration tool — and GoTrue's
provider settings are not in the database, so no SQL reaches them. The Supabase CLI is not
installed on this machine. The Google client additionally requires account ownership and
consent-screen branding decisions.

The Supabase half *could* be automated through the Management API with a personal access
token, but that would route a production OAuth client secret through an agent session for no
saving over one dashboard paste.

## Acceptance criteria

- `curl -s -H "apikey: $ANON" https://cqgzckghgoyzijxgbncw.supabase.co/auth/v1/settings`
  reports `"google": true`.
- `curl -s -o /dev/null -w '%{http_code}' ".../auth/v1/authorize?provider=google"` returns a
  302 to `accounts.google.com`, not a 400.
- Clicking "Mit Google anmelden" on `https://app.gut8erpro.de/login` completes and lands on
  the dashboard, with a matching row in the `User` table (created by the callback route).
- The same works on a second device — the OAuth flow is PKCE within one browser, so this
  confirms the callback, not the mail-link behaviour that ADR 0002 covers.

## Found while triaging — not fixed here

- **The Apple button is dead in exactly the same way.** `apple: false` on the same probe, and
  `signInWithApple` sits directly below `signInWithGoogle`. Sign in with Apple additionally
  needs a paid Apple Developer account and a Services ID. Needs its own ticket.
- **OAuth signup bypasses the signup wizard and Stripe.** The callback creates a bare `User`
  row; there is no subscription gating in `src/lib/supabase/middleware.ts`, so a Google
  signup reaches the dashboard with no trial and no business details — fields the report
  forms and invoices expect. Worth deciding before Part C opens this to the public.

**2026-09-14 (later) — entitlement gate implemented. The hole is wider than Google.**

Queried the live database before writing anything, and the picture changed the fix:

```
total users : 4   plan=PRO : 4   plan=FREE : 0
PRO but no stripeSubscriptionId : 4
stripeSubscriptionId ever written by the webhook : 0
stripeCustomerId present : 4
trialEndsAt : all four expired between 2026-08-12 and 2026-09-01
```

Two things follow. First, `completeSignup` sets `plan: 'PRO'` and `trialEndsAt = now + 7d`
itself (`src/lib/auth/actions.ts:116`), before Stripe is involved — so an email signup that
abandons Checkout is entitled too, not just an OAuth one. Second, and more serious: **the
Stripe webhook has never successfully written a subscription for any user.** All four have a
`stripeCustomerId`, so Checkout sessions were created; none has a `stripeSubscriptionId`,
which the webhook sets in the same `update` as `trialEndsAt`. All four trials lapsed weeks
ago and all four are still PRO, because the only thing that downgrades is a webhook that
never arrives. The four are gmail.com addresses created 2026-08-05 to 2026-08-25 — the
owner's own test accounts, so no revenue is involved, but the mechanism is proven broken.
This lines up with the one check `cutover-wizard.sh` left SKIPPED: confirming
`STRIPE_WEBHOOK_SECRET` matches the live endpoint's signing secret.

### What was implemented

- **`plan: 'FREE'` set explicitly in `/auth/callback`.** The root cause: an OAuth signup
  inherits `@default(PRO)` from the schema. Done at the call site rather than by changing the
  schema default, so no migration has to run against production.
- **`getEntitledUser()` in `src/lib/api/auth.ts`** — authentication plus entitlement in one
  call, asking only `plan === 'PRO'`. The billing nuance (`past_due` is not entitled,
  cancelled and paused downgrade) stays in the webhook, which is its only writer.
- **Applied to the 20 paid routes** — all of `reports/**`, `ai/**`, and `stats` — returning
  402 with `{ error: 'Subscription required' }`.
- **Deliberately left open** to an authenticated-but-unentitled user: `stripe/checkout`,
  `stripe/portal`, `stripe/billing` (otherwise they cannot subscribe), `settings` (the client
  learns its own plan there), and `account/export` + `account/delete` (GDPR rights should not
  sit behind a paywall).
- **Client redirect in `(app)/layout.tsx`** to `/settings/billing` for a FREE user, skipping
  `/help` and `/settings` so there is no loop and the billing page stays reachable. This is
  UX only — the API refusal is the actual gate.
- **`src/lib/api/auth.test.ts`** — 7 cases, including "no row in our database" and the
  distinction between 401 and 402.

Verified: `tsc --noEmit` clean, 716 unit tests pass, `npm run build` succeeds, biome clean on
every touched file (the 3 remaining warnings in `reports/[id]/generate/route.ts` are
pre-existing `noNonNullAssertion` hits unrelated to this change).

### Deliberately not done

- **Trial-expiry enforcement.** Gating on "trial lapsed and no subscription" would lock all
  four existing accounts out immediately, and — with the webhook not delivering — would
  eventually lock out a genuinely paying customer too, since the webhook is what would
  restore them. It belongs after webhook delivery is verified, not before.
- **Removing the premature `plan: 'PRO'` from `completeSignup`.** Same dependency: with the
  webhook down, a real customer would pay and never be promoted. This is the change that
  closes the abandoned-checkout hole, and it should ship the day the webhook is confirmed.
- **The schema default.** `plan Plan @default(PRO)` in `prisma/schema.prisma` is still a
  landmine for any future code path that creates a user without naming a plan. One-line
  migration, wants its own PR.

**2026-09-14 (later still) — gate scope corrected to match the product rule.**

The owner clarified what a subscription actually buys: **creating** reports (and the AI
features), not access to work already produced. A lapsed subscriber keeps their account and
must still be able to open, edit, export and send every report they have already made. The
first pass gated all of `reports/**`, which would have locked a lapsed subscriber out of
their own PDFs and invoice history — wrong, and rewritten.

**Gated (402) — seven handlers:**

```
POST /api/reports                              create a new report
POST /api/reports/[id]/generate                AI report generation
POST /api/reports/[id]/calculation/auto-fill   AI auto-fill
POST /api/ai/analyze-photo | detect-plate | detect-vin | ocr
```

**Open to a lapsed subscriber:** every GET; every PATCH/DELETE on an existing report
(accident-info, vehicle, condition, calculation, invoice, photos, signatures); report export
and send; `photos/process` (image resizing with sharp — infrastructure, not AI); stats;
notifications; settings; the three Stripe routes; and `account/export` + `account/delete`.
`GET /api/reports` lists reports and is open; `POST` on the same file creates one and is
gated — the gate is per-handler, not per-file.

The blanket redirect in `(app)/layout.tsx` was removed for the same reason: an unsubscribed
user now reaches the whole app normally. Instead `createReport` recognises the 402 and throws
`SubscriptionRequiredError` (`src/lib/api/errors.ts`), and the dashboard routes that one case
to `/settings/billing` with a message saying existing reports stay available
(`subscriptionRequired`, added to both locales at full parity).

Verified again after the rewrite: `tsc --noEmit` clean, 716 unit tests pass, `npm run build`
succeeds, biome clean on every touched file.

### One loophole this policy leaves open, by design

Editing an existing report stays available indefinitely, so a lapsed subscriber could in
principle reuse one report shell for new assessments rather than creating a new one. That
follows directly from "they keep access to their existing work" and is the owner's call — it
is recorded here rather than quietly closed.
